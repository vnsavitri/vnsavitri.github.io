The design choice

Each agent owns a workflow end to end: what it reads, which tools it can call, what artefacts it produces, and where it stops.

The product implication

Instead of one giant “finance assistant”, teams can choose narrow, inspectable workers with different permissions and approval paths.

Source: README / Agents table · Agent plugin source

It produces work product, not a final decision.

The key safety pattern is the hand-off between machine-generated artefacts and qualified human judgement.

01 / inputQuestion, file, period

“Review this earnings event” or “reconcile this trade date”.

02 / retrieveRead approved sources

Filings, transcripts, market data, ledgers, CRM, or internal documents.

03 / reasonApply domain skill

Run the method, rules, model, or checklist captured in the plugin.

04 / draftStage artefacts

Model, note, exception report, pack, or escalation packet.

05 / reviewHuman sign-off

Qualified professional verifies, marks up, approves, or rejects.

Hard boundary from the repo

These agents do not make investment recommendations, execute transactions, bind risk, post to a ledger, or approve onboarding. Every output is staged for human sign-off.

The system is designed to stop before authority.

That boundary is the repo’s clearest product decision.

What the agents can do

  • Read approved inputs and connected sources.
  • Apply a repeatable domain method.
  • Draft models, memos, notes, reports, reconciliations, and packs.
  • Flag gaps, exceptions, and evidence for review.

What they do not do

  • Make investment recommendations.
  • Execute transactions or bind risk.
  • Post to a ledger.
  • Approve onboarding or replace qualified sign-off.

What your implementation still needs

Identity, tenancy, and least-privilege access.
Evidence retention, provenance, and audit trails.
Evaluation datasets for accuracy and escalation behaviour.
Policy mapping, monitoring, incident response, and rollback.

Use the manifests as a contract, not as a black box.

name: earnings-reviewer
model: claude-opus-4-7

system:
  file: agents/earnings-reviewer.md
  append: "Produce files in ./out/"

tools:
  - read
  - grep
  - glob
  - mcp: factset
  - mcp: daloopa

callable_agents:
  - transcript-reader
  - model-updater
  - note-writer

Make the contract explicit

  • Input: ticker, reporting period, and approved source IDs.
  • Tools: only the connectors needed for that workflow.
  • Outputs: named artefacts with a known review state.
  • Stop conditions: missing evidence or approval required.
  • Write boundary: one worker assembles the final file.

Done condition

Run one representative case end to end, inspect every citation and calculation, and have a qualified reviewer approve the output shape before widening scope.

Source: earnings-reviewer/agent.yaml · agent prompt

Earnings Reviewer, end to end.

The repo’s workflow logic translated into a simple sequence.

INPUTTicker + period

One covered name and one reporting event.

READTranscript + filings

Pull evidence through FactSet and Daloopa.

UPDATECoverage model

Drop actuals, roll estimates, and flag variance.

DRAFTEarnings note

Headline read, drivers, estimate changes, valuation update.

REVIEWSenior analyst

Mark up and approve before downstream use.

What this teaches

Good agent design is about artefact choreography: each step produces something the next step can inspect, validate, or improve.

What to measure

Evidence coverage, formula integrity, variance accuracy, missing-data escalation, reviewer edits, and time saved per event.

Source: Earnings Reviewer prompt · cookbook

Ship the workflow boundary, not just the prompt.

A useful reference repo becomes a reliable internal product only when the surrounding controls are real.

Data & permissions

  • Scope connectors per agent.
  • Validate identities and tenant boundaries.
  • Keep sensitive data out of prompts and logs where possible.

Quality & evidence

  • Build golden cases and regression tests.
  • Require source references for material claims.
  • Check models, formulas, and tie-outs.

Operations & review

  • Make approval states visible.
  • Monitor failure and escalation rates.
  • Keep a rollback path for skills and connectors.

The smallest credible pilot

One workflow. One data path. One output artefact. One qualified reviewer. Ten representative cases. A clear go / no-go rule.
