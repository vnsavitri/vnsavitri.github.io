Plain English

OpenCut wants to be a cross-surface, extensible video editor.

The idea

One editor, many surfaces

The rewrite is organised around a Rust core that can support browser, desktop and mobile experiences from one codebase.

The leverage

Automate the boring parts

The README points towards an Editor API, headless mode, scripting, and an MCP server for AI agents.

The reality

Still early

The checked-out rewrite has a minimal web app, a tiny API, and an early GPUI desktop shell. The classic version is the usable product today.

Why it matters

Open source changes the control surface of editing.

01

Own the workflow

For teams, a programmable editor can be shaped around brand rules, review loops, asset stores and delivery targets.

02

Compose instead of copy

A plugin-first architecture creates a place for integrations: effects, importers, generators, automations and internal tools.

03

Make agents useful

An MCP server and scripting surface could let an agent inspect, edit, render and hand work back into a human editor.

04

Reduce platform lock-in

MIT licensing and self-hostable building blocks make the project easier to study, fork and adapt, subject to the repository’s maturity.

Use case canvas

Where this could become more than a video editor.

Creator workflows

Short-form repurposing

Import a long recording, cut a set of vertical clips, apply a brand template and export a review pack.

Best fit: scripting + headless rendering, once available.

Product teams

Branded content ops

Build an internal panel that assembles approved footage, copy, captions and product shots into repeatable edits.

Best fit: Editor API + plugins, as proposed by the README.

AI prototyping

Human-in-the-loop agents

Let an agent propose edits, explain its choices and hand a structured project back to a person for review.

Best fit: MCP server + visible editor state.

The most useful signal is not the number of folders. It’s the boundary between what is implemented, what is scaffolded, and what is promised.

Evidence before aspiration

The current rewrite is scaffolding, not a finished editor.

Web

Shell present

The home route renders “hello world!” and the editor route says “Coming soon.” The app is wired with TanStack Start/Router and Vite.

API

Minimal service

The Cloudflare Worker exposes a status route, a health route and a typed echo endpoint through Elysia.

Desktop

Window + panels

The GPUI app opens an OpenCut window with browser, preview, inspector and timeline entities. Its own README calls it “Very early”.

Read this correctly

OpenCut is interesting because the seams are being designed early. It is not yet a drop-in replacement for a mature editor.

Planned contract

The rewrite is aiming for composability, not only features.

Planned

A stable surface for manipulating projects and editor state from tools, plugins or other applications.

Planned

Third-party plugins

Extensions are meant to be first-class, enabled by a plugin-first architecture.

Planned

MCP server

A bridge for AI agents to work with the editor through structured tools and context.

Planned

Headless + scripting

Automation and a scripting tab would let repeatable editing workflows run with less manual clicking.

Design implication

The product’s long-term advantage could come from a shared project model and clear capability boundaries. That is an architectural opportunity, not yet a validated product outcome.

Trade-offs to watch

OpenCut’s promise depends on hard problems it hasn’t solved yet.

Cross-platform parity

One codebase reduces divergence, but browser, desktop and mobile still have different media, GPU and filesystem constraints.

Plugin trust

Plugins increase capability and risk. Permissions, sandboxing, versioning and review become product features.

Agent reliability

MCP access is only useful if edits are observable, reversible, grounded in project state and safe to render.

Media performance

Editing workloads are dominated by decoding, compositing, audio timing, GPU acceleration and export correctness.

The repository gives evidence of the intended direction. It does not yet establish production performance, feature parity or ecosystem adoption.

How to implement: from clone to contribution.

The current implementation path is a workspace setup and inspection loop. Feature development comes after you understand which surface owns the behaviour.

Web development is the easiest starting point. Desktop builds use GPUI and may require platform graphics packages, especially on Linux.

Step 03 · Extend

Pick an ownership boundary before writing code.

UI feature

Start in web

Define the user interaction in the web route or component tree. Keep state close to the surface until a shared model exists.

Service feature

Start in API

Add a typed Elysia route, then decide how the web or desktop surface calls it. Keep health and failure states visible.

Native feature

Start in desktop

Use the existing GPUI panel entities and preserve state ownership. The desktop README warns that this surface is very early.

Forward-looking integration

For plugins, MCP or headless rendering, first define the project representation, permissions, undo/redo semantics and validation hooks. The README names these directions, but the current checked-out tree does not yet expose their implementation.

Sources: apps/ · planned capabilities
Step 04 · Validate

Make “it runs” a small part of done.

✓Can a new developer reproduce the baseline using the documented commands?
✓Does the change belong to web, API, desktop or a genuinely shared layer?
✓Are failure, loading, permissions and undo/redo states explicit?
✓Does the feature preserve a path to plugins, scripts or agents later?
Contribution reality

Know the project’s current invitation

The README says outside contributions aren’t set up yet while the architecture is being designed. That means the best immediate contribution may be discussion, issue reports, experiments or following the Discord rather than assuming a normal PR flow.
