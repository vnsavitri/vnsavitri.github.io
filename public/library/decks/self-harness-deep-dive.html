Self-Harness

Harnesses that improve themselves.

The idea is simple: let an agent study its own execution failures, propose small changes to the scaffolding around it, and keep only edits that survive regression tests.

Paper explainer
A plain-English guide to the paper’s mechanism, evidence and practical implementation.
Zhang et al., “Self-Harness: Harnesses That Improve Themselves” · arXiv:2606.09498v3
The short version
02 / 22

An agent can improve its operating system without changing its brain.

Self-Harness keeps the model weights fixed. It evolves the surrounding protocol: prompts, tools, runtime controls, verification and recovery.

1

Mine

Run tasks. Use verifier-grounded traces to cluster recurring failure mechanisms.

2

Propose

Ask the same model for diverse, minimal edits tied to those mechanisms.

3

Validate

Regression-test each candidate on held-in and held-out tasks. Promote only non-regressive gains.

The problem
03 / 22

Agent performance is more than model capability.

The harness is the layer that decides what the model sees, what it can do, when it checks its work and how it recovers.

Same model ≠ same agent.

Two harnesses can produce different outcomes because execution protocol changes behaviour over long horizons.

Harness = prompts + tools + memory/state + verification + policies + runtime control.
Source: §§1–2.
Section break · the shift
04 / 22

Who gets to improve the harness?

Self-Harness moves improvement inside the evaluated agent, while keeping the model and evaluator fixed.

Human engineering

Experts inspect failures and manually revise the scaffold.

Meta-Harness

A stronger external agent guides improvement of a weaker target.

Self-Harness

The evaluated agent improves the very harness it runs through.

The paper studies a bounded middle ground, not open-ended recursive self-improvement.
Source: Figure 1; §1.
Deep dive · mechanism
05 / 22

Evidence becomes a harness state transition.

Every round starts with a current harness hₜ and ends with either a tested update hₜ₊₁ or no change.

01 · observeWeakness mining

Run the fixed model. Collect traces and verifier outcomes. Cluster recurring failure signatures.

→
02 · hypothesiseHarness proposal

Generate several diverse but minimal edits, each tied to one mechanism and one editable surface.

→
03 · gateProposal validation

Regression-test held-in and held-out tasks. Reject trade-offs; merge compatible winners.

Fixed throughout: model weights, evaluator, task protocol, non-editable runtime settings. Allowed to change: the surrounding harness.

This separation is the paper’s causal story: if only the harness changes, measured gains are attributable to that layer within the protocol.

Deep dive · stage 3
08 / 22

Promotion is conservative by design.

A candidate must improve at least one split without degrading the other.

Δin ≥ 0   and   Δho ≥ 0
and max(Δin, Δho) > 0

When evaluation is stochastic, the paper repeats candidate evaluation and applies the rule to aggregate pass counts.

accept

Better on held-in, no worse held-out.

Or better on held-out, no worse held-in. Compatible winners can be merged.

reject

Trade-off, invalid surface or failed evaluation.

Rejected candidates stay logged. The active harness does not change.

Why it matters: the gate is the paper’s defence against overfitting the proposer to the failures it has seen.

This is a promotion rule, not a guarantee of safety outside the measured protocol.
Source: §3.4; Algorithm 1.

Evidence · mechanism, not magic
12 / 22

The retained edits are workflow interventions.

The paper reports targeted changes, not simply longer prompts.

MiniMax M2.5

Create earlier. Handle schemas. Stop loops.

Edits target missing required artefacts, structured tool content and stalled tool-use loops.

Qwen3.5

Precheck. Retry with discipline. Recover.

Edits target dependencies, repeated failed commands, exploration cycles and artefact recovery.

GLM-5

Persist state. Move to implementation.

Edits target environment persistence and the transition from exploration to testing.

Interpretation: the same base model family can benefit from different harness mechanisms because its failure patterns differ in context.

Evidence level: quantitative benchmark results plus qualitative trace/code analysis; no claim of general-purpose autonomy.

The proposer sees failure evidence from held-in tasks. Held-out tasks are kept behind the promotion gate.

Still a bounded claim.

This is the paper’s strongest practical lesson: self-improvement needs an externalised test boundary.

How-to · step 3
17 / 22

Turn traces into an evidence bundle.

Ask an analysis pass to find repeated, actionable mechanisms across failed runs.

Good pattern: “The agent repeatedly deletes or never creates the verifier-required artefact after a tool error.”

Weak pattern: “The agent timed out.”

1 · filter

Select failed records with verifier evidence.

2 · attribute

Separate terminal cause from agent-side behaviour.

3 · cluster

Group only when cause + causal status + mechanism agree.

4 · rank

Order by support and likely actionability.

Keep the evidence bundle separate from the edit: diagnosis should not silently prescribe the fix.
Source: §3.2; implementation framing is adapted.
How-to · step 4
18 / 22

Generate candidates in parallel. Promote them like code.

A proposal is a hypothesis about behaviour. Evaluation decides whether it becomes part of the harness.

proposeCandidate Δ₁

Target: missing artefact
Surface: bootstrap instruction

proposeCandidate Δ₂

Target: tool loop
Surface: runtime middleware

proposeCandidate Δ₃

Target: bad recovery
Surface: error policy

Evaluate each branch

Run current and candidate harnesses on the same held-in and held-out tasks. Record split-wise deltas, repeats, changed surfaces and decision.

Merge only compatible winners

If all candidates fail, keep hₜ. If several pass and don’t conflict, merge into hₜ₊₁. Log rejected branches for future analysis.

Treat the harness lineage as a testable artefact, not a hidden prompt file.
Source: §§3.3–3.4; Algorithm 1.
How-to · reference pseudocode
19 / 22

One implementation shape.

Keep the orchestration boring. The intelligence belongs in the evidence, proposal and verifier interfaces.

Important: this is a practical adaptation of the paper’s algorithm, not a drop-in library.

for round in rounds:
  baseline = evaluate(model, harness, tasks, verifier)
  evidence = mine_failures(baseline.failures)

  proposals = propose_parallel(
      model, harness, evidence,
      editable_surfaces, width=K)

  accepted = []
  for proposal in proposals:
    candidate = apply(harness, proposal.edit)
    result = evaluate(model, candidate, tasks, verifier)
    if non_regressive(result, baseline):
      accepted.append(proposal)
    else:
      log_rejection(proposal, result)

  harness = merge(harness, accepted)
  save_lineage(harness, accepted)
Implementation advice: make every function emit structured logs and versioned artefacts.

How-to · where it fits
20 / 22

Where this pattern is useful.

Choose environments with repeatable tasks, meaningful verifiers and a harness you actually control.

coding agents

Repository repair and local tooling

Detect loops, missing patches, skipped tests or broken recovery. Promote narrow verification and runtime changes.

Example: a coding harness that learns to run the targeted test before declaring success.

research agents

Evidence and provenance workflows

Detect unsupported claims, missing citations or incomplete extraction. Promote provenance checks and source-of-truth retrieval.

Example: an agent that learns to attach a source note before finalising a literature brief.

ops agents

Tool-driven product operations

Detect stale state, repeated failed actions or partial writes. Promote confirmation, recovery and bounded retry policies.

Example: an agent that learns to re-read state after a write and stop after a fixed retry budget.

Not a fit yet: open-ended creative work without reliable verifiers, high-stakes changes without strong approval gates, or environments where traces contain sensitive data you can’t safely process.

Use-case examples are recommendations, not experiments reported by the paper.
Practical adaptation based on the paper’s mechanism and limitations.
Boundaries
21 / 22

Self-improvement is only as good as its boundary conditions.

The paper’s acceptance rule is useful, but it is not a complete safety case.

Benchmark overfitting

Accepted edits may encode benchmark-specific failure patterns. Add cross-domain, temporal or adversarial regression tasks.

Verifier weakness

A weak or gameable verifier can reward the wrong behaviour. Validate the evaluator independently.

Trace contamination

Proposer context can leak held-out information or sensitive data. Enforce split isolation and redaction.

Reversible promotion

Version every harness, keep rejected candidates, require approvals for high-impact surfaces and make rollback cheap.

Stronger gates

For consequential workflows, add invariants, human review, canary runs, policy checks and failure budgets.

Auditability

Store the evidence, proposal rationale, diff, evaluation repeats and accept/reject decision for every transition.

The paper itself says higher-stakes harness changes need stronger acceptance gates than pass-rate non-regression.
Source: conclusion; §§3.4 and 4.1.
Takeaways
22 / 22

Build agents that can learn from their own execution, with receipts.

The useful unit of progress is not a clever prompt. It’s a reversible, evidence-backed harness transition.

1

Observe behaviour

Record traces and verifier-grounded failure mechanisms.

2

Change the scaffold

Propose diverse, minimal edits to declared surfaces.

3

Earn promotion

Regress on what the proposer didn’t see. Keep the diff, evidence and decision.
