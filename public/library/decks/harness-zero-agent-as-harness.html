Harness distillation via agent-as-harness

What if the harness could teach the model?

Harness-Zero turns an evolved agent harness into training-time guidance, then distils the behaviours it induces into model weights. At deployment, the specialised scaffolding can be removed.

Plain-English summary

Keep the behaviour. Lose the scaffolding.

An optimised harness may know how an agent should inspect state, use tools, verify outputs, or avoid risky moves. Harness-Zero uses a reviewer agent to translate that guidance into corrections the student can execute under its ordinary, minimal harness.

23.3 → 44.3%

Macro-average task success after fine-tuning Qwen3.5-9B. The distilled student runs with the fixed target harness alone, without the evolved harness, private reference harness, or reviewer.

The problem

Runtime scaffolding is powerful, but its gains are sticky.

Specialised harnesses improve agents

  • Tools and workflows extend what the model can do.
  • Middleware can block, verify, or reshape actions.
  • Skills and memory supply procedural guidance.

But deployment inherits the scaffolding

  • A shared harness leaves domain-specific gains unused.
  • Many harnesses add routing, context, calls, and cost.
  • Harness assumptions can go stale as models change.

The research question: can we use a specialised harness at training time, then make its useful behaviours available under a single fixed target harness?

Four moving parts

Same model. Different jobs.

The trick is to separate the student’s visible operating loop from the harnessing agent’s private review context.

Key constraint
Every accepted correction must be a complete response valid in the student’s native action space.

h

Target harness. Fixed, minimal runtime interface used at deployment.

h*

Evolved harness. Domain-specific scaffolding optimised on training tasks.

K

Reference harness. Private adaptation of h* for review, relative to h.

πH

Harnessing agent. Reviews proposals and passes or replaces them.

The core mechanism

Translate guidance at the response boundary.

01 · STUDENT

Propose

The student produces yₜ under the fixed target harness h.

02 · REVIEW

Inspect privately

πH reads the current state, proposal, and reference harness K.

03 · DECIDE

Pass or replace

Sound proposals pass; weak ones get the smallest coherent correction.

04 · EXECUTE

Learn from reality

The accepted response runs through h; its observation returns to the student.

Read the result honestly

Harness-Zero narrows the harness. It doesn’t erase it.

Reviewer quality

The method depends on a capable harnessing model. With weaker reviewers, intervention can become harmful.

Collection cost

Reviewing every proposal adds a model call at collection time. The paper reports 2.4× mean USPTO latency.

Expressivity

Some harness mechanisms, especially context management, are not directly expressible as student responses.

The strategic implication: harness development can become a scalable source of training data. Better models build better scaffolds; the scaffolds return reusable behaviour to the weights.

Step-by-step guide

Six bounded moves from harness to weights.

Define h

Freeze the deployment interface: tools, context contract, turn limits, and observables.

Evolve h*

Use training failures to improve domain-specific tools, middleware, skills, and memory.

Adapt into K

Convert runtime interventions into review criteria and student-native action recipes.

Wrap πS

At each response boundary, send the proposal and new visible events to πH.

Collect Dreview

Keep unchanged proposals and minimal corrections; hide private reviewer reasoning.

Fine-tune + remove

SFT accepted responses under h, then evaluate the student under h without h* or πH.

16 / 21
The adaptation step

Change the audience, not the intent.

Tools

Student-facing tool becomes a specification for an action recipe the reviewer can construct using h.

Middleware

Execution rule becomes review middleware: a private alert that fires when a proposal violates the intent.

Skills

Instruction becomes a diagnostic criterion: what evidence should appear before the reviewer passes?

Memory

Prior experience becomes failure patterns and intervention guidance, not hidden state injected into the student.

Domain prompt

State the review policy explicitly: when to intervene, how much to change, and what the student can observe.

Grounding rule

If evidence is missing, propose an h-valid check. Never consult hidden solutions or verifier feedback.

Reference pseudocode

Keep the reviewer private, the trajectory legal.

agent_as_harness.py
for event in student_rollout:
  proposal = student.propose(visible_state)
  decision, replacement = reviewer.review(
      visible_state, proposal, K, private_history
  )

  accepted = proposal if decision == "PASS" else replacement
  observation = target_harness.execute(accepted)
  reviewed.append(accepted, observation)
  visible_state = visible_state + accepted + observation

# SFT on accepted responses only;
# mask reviewer-perspective reasoning.

Three non-negotiables

  • Replacement is a complete h-valid response.
  • Reviewer cannot inspect hidden task solutions.
  • Only accepted response + observation enters the student trajectory.

(distilled student, h)
No h* · no K · no πH.

How to know it worked

Evaluate transfer, not just collection success.

Hold out tasks and domains

Keep a disjoint test set. If possible, add a held-out harness or model to test portability.

Compare the right baselines

Base under h, base under h*, distilled under h, generic harnesses, and direct teacher distillation.

Mine harness-exclusive behaviours

Detect procedures that appear under h* but not h, then score recovery under h after distillation.

Audit legality and privacy

Count unavailable-tool calls, leaked reviewer reasoning, hidden-state access, and turn-limit failures.

Do not optimise the wrong number

Harness-Zero’s ablation shows that high collection success can produce poor distillation. Oracle-answer review reached 98.6% collection success but only 15% test pass@1, while K-guided review reached 59.4% collection success and 30% test pass@1.

Measure whether the student learns reusable procedure, not whether the temporary teacher can finish the training tasks.

Where this could be useful

Start with behaviours you can observe and verify.

AI product agents

Distil reliable inspect → act → verify routines into a smaller deployment model for support, operations, or internal workflows.

Scientific agents

Turn domain harness checks into model behaviour while keeping the execution surface minimal and auditable.

Tool-heavy knowledge work

Transfer disciplined state management, mutation read-back, and completion criteria without carrying a large generic tool suite.

A sensible first pilot: choose one workflow with clear state transitions, a small action space, and measurable procedural failures. Spreadsheet-like data mutation is a better starting point than open-ended research reasoning.

The takeaway

Harnesses can be more than runtime scaffolds. They can become training infrastructure for the behaviours we want models to carry.

The strongest lesson is not “add a reviewer”. It is: translate specialised guidance into the student’s legal action space, preserve the student’s state, and evaluate what survives when the scaffolding is gone.
