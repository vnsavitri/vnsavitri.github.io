A deep dive from the chatbot era into the decision era

Jev is not a smaller chatbot.
It is a decision engine.

What happens when an AI model stops generating prose and starts returning the typed, probabilistic judgements that software actually needs?

Start here · plain-English summary

LLMs write. Jev judges.

Jev takes messy state, asks several tightly defined questions, and returns typed answers such as a choice, a score, or the probability that a statement is true.

fastNo token-by-token prose generation. Questions can be evaluated in parallel.
typedOutputs are constrained to the structure you define, so your code does not need to parse a paragraph.
composableUse confidence and probabilities to branch, route, escalate, or combine judgements in ordinary code.

Best mental model: a frontier-intelligence function call — unstructured state in, typed probabilistic decisions out.

Before the deep dive

Use it where the answer has a shape.

Choice

Pick one path

Route a support ticket to billing, technical, or sales. The options are declared before the model answers.

Score

Place it on a scale

Estimate frustration, risk, severity, or fit against a rubric with named levels.

Noul

Is this true?

Return a 0–1 probability for a focused yes/no judgement, such as “does this message request a refund?”

The name “Noul” is TypeSafe’s primitive for a probability that a statement is true. It is not a general-purpose answer generator.

01 / The idea

Why this is different

The interesting move is not “make an LLM cheaper”. It is “stop forcing a text generator to behave like a typed decision API”.

↘
From prose generation to software-native decisions04 / 19
The core distinction

Strings are powerful. They are also a poor interface.

Typical LLM workflow
  • Generate a sequence of tokens, one after another.
  • Ask for JSON or a label inside the generated text.
  • Parse, validate, and handle refusals or malformed output.
  • Confidence is usually an extra request, not a native signal.
Jev / System One workflow
  • Ingest state and evaluate typed questions.
  • Return values inside a structure declared up front.
  • Receive probability distributions for Choice and Score.
  • Compose the results with deterministic application code.

Design implication: put language understanding at the fuzzy edge, then let ordinary code own the workflow, policy, thresholds, and side effects.

The performance idea

One state. Many independent judgements. One call.

Instead of making a workflow wait for one classifier, then another, Jev evaluates questions independently against the same state. You can ask for routing, urgency, and frustration together.

One ticket“The Stripe integration keeps failing. I’m losing sales.”
→
Fan-out
departmentfrustrationurgent?
→
BranchRoute, prioritise, and escalate with code.

Key pattern: ask every question your code might need, even if some answers will be ignored for this input. The API is designed for speculative fan-out.

02 / Evidence & limits

Fast is useful.
Evidence is better.

Jev looks compelling for the right task. The right question is not “is it better than an LLM?” but “does it fit this decision surface, with acceptable error and uncertainty?”

The claim needs a precise definition

Type-safe is not the same as correct.

What it can rule out: output outside the structure you specified. No invented JSON key, no free-form prose where a Choice was required.

What it cannot rule out: a wrong classification, a biased rubric, missing context, or a confident but mistaken judgement.

Think in two axes

Schema validityDid the answer fit the allowed type and options?
↓
Task validityWas the judgement right for your data, policy, and stakes?
Sources: article + TypeSafe introduction; wording intentionally distinguishes type errors from task errors.11 / 19
Reliability is an architecture question

Confidence should change what the system does next.

LowDo not act. Escalate, clarify, or fall back.
MediumConfirm, gather more context, or review.
HighAutomate low-risk actions; keep high-risk confirmation.

Risk sets the threshold

Showing the wrong screen is recoverable. Approving a transfer is not. Use different confidence gates for each action.

if confidence < 0.5:
route_to_human()

if high_stakes and confidence < 0.9:
ask_for_confirmation()

Prompt injection: the article reports informal tests suggesting Jev may resist some attacks better because state and instructions are separate. Treat that as a hypothesis until you run adversarial evaluations on your own workflow.

03 / Build it

Start with a question.
End with a workflow.

The implementation is small. The product work is deciding what the model is allowed to judge, what evidence it sees, and what the surrounding code does with uncertainty.

→
A step-by-step implementation guide13 / 19
A practical build sequence

Four moves from idea to safe prototype.

01
Define the state

Pass the smallest useful record: text, metadata, policy, or structured context.

02
Split judgements

Ask one focused question per dimension. Avoid “analyse everything and decide”.

03
Batch the call

Mix Choice, Score, and Noul in one request when they share the same state.

04
Own the branch

Use probabilities and confidence in application code. Gate side effects by risk.

Rule of thumb: if a judgement needs extended reasoning, decompose it into smaller factors and compose the result in code.

Source: TypeSafe primitives and confidence documentation14 / 19
Official SDK shape, simplified for teaching

Ask three questions in one request.

python · typed decisions
# pip install typesafe-sdk
from typesafe_sdk import Choice, Noul, Score, TypeSafeClient

client = TypeSafeClient()
response = client.system_one(
    state=ticket,
    questions={
        "department": Choice(
            instructions="Which team should handle this?",
            criteria={"billing": "Payment or subscription issues",
                      "technical": "Bugs or integration problems",
                      "sales": "Pricing or account questions"}),
        "frustration": Score(
            instructions="How frustrated does the customer appear?",
            criteria=["Calm", "Frustrated", "Very angry"]),
        "is_urgent": Noul(
            instructions="Does the message convey urgency?"),
    },
)

Do not stop at the API call

Make the surrounding code boring.

JevReturns Choice, Score, Noul, probabilities, and confidence.
→
Policy layerApply thresholds, weighting, permissions, and business rules.
→
Side effectRoute, notify, retrieve, ask for confirmation, or do nothing.

Good decomposition

“How severe is the bug?”
“How frustrated is the customer?”
“How complete is the reproduction?”

Bad decomposition

“Read this ticket, reason about everything, and decide what the company should do.”

Architecture payoff: when priorities change, change weights and thresholds in code instead of rewriting one giant prompt.

Worked design example

Game NPCs are a good fit for fuzzy edges.

Imagine a nemesis system that needs fast, explainable signals rather than a conversational monologue. Jev can score state; deterministic code can own the actual game rules.

Why this is interesting: the AI supplies a fast judgement about a rich state; the game remains testable because the state machine still owns the action.

A decision checklist

Use Jev when the decision surface is narrow.

✓
There is a small answer space.Choice, ordered score, or probability of a defined statement.
✓
Latency or cost matters.You are making many decisions, or the UX cannot wait for prose.
✓
You can define the state.The model gets the relevant evidence without needing a long discovery phase.
✓
You can test the rubric.You have examples, labels, reviewers, or a golden set to measure task validity.
✓
You want code to own policy.Thresholds, weights, permissions, and side effects stay inspectable.
✓
You do not need prose generation.If users need a nuanced explanation, pair the decision model with a generator.

Do not use it as a universal LLM replacement. If the task is open-ended reasoning, creative generation, or evidence synthesis, use a model and workflow designed for that job.
