01 · Plain-English summary

Think of Unsloth as a shortcut from “I have a model idea” to “I can run, adapt, and serve it.”

Run locally

Chat with supported models on your own machine, with model files and workflows kept close to your data.

Train with less friction

Use fine-tuning and reinforcement-learning workflows without hand-assembling the whole Python stack.

Connect your agents

Expose a local model through compatible APIs, MCP, and integrations for tools such as Codex and Claude Code.

The useful idea is not “one more model UI”. It is a local model workbench that covers the loop: load → adapt → evaluate → export → serve.
Sources: README features · “Run and train LLMs…”; Unsloth Start · “connects Claude Code, Codex and other agents to local models”.

Mounts are the boundary

$PWD maps to /workspace/host. The Hugging Face cache avoids repeated model downloads. A named Studio volume retains accounts, chats, outputs, exports, and runs.

GPU access is explicit

The NVIDIA quickstart uses --gpus all. On Linux, Docker and NVIDIA Container Toolkit are prerequisites; the guide lists NVIDIA driver 570.26 or newer.

Sources: Docker guide · “the three -v flags keep your files, models and Unsloth Studio data”; “Requirement: NVIDIA driver 570.26 or newer”; Docker image README · volume semantics.
06 · What it optimises

Unsloth’s value proposition is efficient experimentation.

2×faster

The README claims fine-tuning can be 2× faster with 70% less VRAM and “no accuracy loss”. Treat this as a project claim, not a universal guarantee.

70%less VRAM

Actual gains depend on model, hardware, sequence length, quantisation, batch size, kernels, and the evaluation you run.

Parameter-efficient

LoRA and QLoRA update a smaller set of parameters, which can make adaptation cheaper and easier to iterate.

Reinforcement learning

The repository lists RL methods including GRPO and DPO alongside supervised fine-tuning.

Deployment-minded

Export pathways include GGUF, NVFP4, FP8, and other formats listed by the project.

Source: README Train & Deploy · “2× faster with 70% less VRAM with no accuracy loss”; the caveat about workload dependence is an interpretation and recommendation.

A local model becomes more useful when other tools can call it.

OpenAI-compatible endpoint

Serve a local model behind an API shape that many existing clients already understand. That can reduce application-side rewiring while you compare local and hosted models.

Important boundary

Tool calling changes the risk profile. A local model can still run code or access mounted files if you give the surrounding system those capabilities. Keep tool permissions and mounts narrow, especially on shared or remote machines.

09 · Step 1

Choose the surface and hardware path first.

Easy start

Desktop

Use the native app when you want the smallest setup surface and don’t need a containerised workflow.

Best for: first experiments, local chat, quick demos.

Recommended here

NVIDIA Docker

Use unsloth/unsloth when you want Studio, JupyterLab, notebooks, caches, and a reproducible GPU environment.

Best for: repeatable workstations, remote GPU boxes, agent experiments.

Code-first

Core

Use the Python package when your notebooks, scripts, or application code are the product.

Best for: pipelines, CI, custom training loops.

Hardware reality check

The Docker guide’s main quickstart is NVIDIA. AMD uses a separate ROCm image and native Linux device-node flags. CPU mode can cover Jupyter, GGUF tooling, and llama.cpp GGUF Studio chat, but not loading Unsloth models or training.

Sources: README install options; Docker guide · AMD and CPU notes.
10 · Step 2 · NVIDIA Linux / WSL

Start the container from the project folder.

bash · quickstart
docker run -d --name unsloth --gpus all --ipc=host \
  --ulimit memlock=-1 --ulimit stack=67108864 \
  -p 8000:8000 -p 8888:8888 \
  -e JUPYTER_PASSWORD="choose-a-jupyter-password" \
  -v "$PWD":/workspace/host \
  -v "$HOME/.cache/huggingface":/workspace/.cache/huggingface \
  -v unsloth-studio:/opt/unsloth-studio \
  unsloth/unsloth

Run it from

Your project directory. That is what becomes /workspace/host.

Keep the volume

Do not replace the named Studio volume with a macOS or Windows host folder.

Read the logs

They include readiness links and first-run password details.

Source: Docker quickstart · command, project-folder mapping, flags, password and volume guidance. The password value above is intentionally a placeholder.
11 · Step 3

Start, inspect, sign in.

Start the container

For a stopped container, run docker start unsloth.

Follow the startup logs

Run docker logs -f unsloth. Ctrl-C stops log following, not the container.

Open Studio

Visit http://localhost:8000 and sign in as unsloth. On first setup, change the generated Studio password.

Choose a model

Use Select model, search the Hugging Face Hub, and choose a quantisation that fits available RAM and VRAM. Avoid variants marked OOM.

Why the password change matters

The guide says Studio shuts down after an hour if the generated first-run password isn’t changed. A reused Studio volume keeps the password already stored on it.

Source: Studio Setup and Chat with a model · start, logs, sign-in, model selection, and password behaviour.
12 · Step 4

Make the environment recoverable before you rely on it.

Persistence recipe

  • Keep the named unsloth-studio volume.
  • Keep your host Hugging Face cache mounted.
  • Keep project files in a versioned host folder.
  • Use explicit passwords for unattended or remote starts.

Password recovery

docker exec unsloth unsloth studio reset-password \
  --username unsloth

The guide says this signs out existing sessions and revokes API keys. No restart is needed.

Update

Pull a new image tag to update the bundled stack, or use the in-container Studio update command where appropriate.

Stop cleanly

Give training time to save a checkpoint on stop. The guide documents a longer Docker stop timeout for this.

Delete intentionally

docker rm -f unsloth deletes the container, but named volumes and mounted caches can survive it.

Sources: Docker guide · password reset, persistence, checkpoint and container lifecycle notes; Docker image README · update and volume details.
13 · Step 5 · Remote access

Remote access is powerful because it is also an exposure decision.

Local-only

Bind ports to 127.0.0.1 and use an SSH tunnel. Good default for a private GPU host.

Cloudflare HTTPS

Use UNSLOTH_STUDIO_SECURE=1 for a public HTTPS link, then protect it with a strong password.

Raw published ports

The guide warns that -p 8000:8000 and -p 8888:8888 publish on every interface. JupyterLab is a full shell.

ssh tunnel pattern
ssh -L 8000:localhost:8000 \
    -L 8888:localhost:8888 user@your-server

Tool and mount boundary

Studio tools are on by default and can run commands inside the container. Mount only folders you’re comfortable granting to the container, and avoid exposing plain HTTP directly to the internet.

Source: Docker Security Notes · published ports, JupyterLab shell, server-side tools, and mounted-folder guidance.
14 · Step 6 · Platform branches

The command changes with the hardware. Don’t cargo-cult the NVIDIA path.

Windows

Docker Desktop + WSL 2

Install Docker Desktop and a current NVIDIA Windows driver, update WSL, and enable the WSL 2 based engine.

No separate NVIDIA Container Toolkit install is required on Windows according to the guide.

AMD

ROCm image

Use unsloth/unsloth-rocm with Linux device nodes such as /dev/kfd and /dev/dri.

The image carries the training stack only, with no Studio or JupyterLab.

CPU

Limited mode

Set UNSLOTH_ALLOW_CPU=1 when you need Jupyter, GGUF tooling, or llama.cpp GGUF Studio chat without a GPU.

Training and loading Unsloth models still require a GPU.

Validation habit

After launch, verify the container can see the expected accelerator before debugging model code. For NVIDIA, the guide suggests checking with docker exec unsloth nvidia-smi.

Source: Docker guide · Windows, AMD, CPU, and GPU troubleshooting branches.
15 · Step 7 · Validation

Declare “done” with a small proof, not a feeling.

Service check

Studio loads at the expected host port and you can sign in.

GPU check

The container sees the intended GPU, and the runtime reports the expected CUDA availability.

Persistence check

Download a small model, restart the container, and confirm the model and Studio account remain available.

Workflow check

Run one prompt, one notebook cell, and one tiny evaluation or export. Record the model, quantisation, hardware, and result.

Port collision

Change the host side, for example -p 8001:8000, then open the matching host URL.

OOM

Unload the Studio model or stop the notebook kernel. Studio and JupyterLab share the same GPU.

Source: Docker guide troubleshooting and usage · GPU checks, port allocation, OOM guidance, and shared-GPU note; validation checklist is a recommendation.

17 · Limitations and evidence

Fast setup doesn’t remove the hard parts.

Hardware still matters

GPU memory, driver versions, CUDA/ROCm compatibility, quantisation choice, and model size determine what “local” means in practice.

Performance claims need a baseline

Measure your own workload. Report hardware, model, batch size, sequence length, quantisation, wall-clock time, VRAM, and quality metrics.

Security is configuration-dependent

Published ports, JupyterLab access, server-side tools, root execution, and broad mounts can turn a convenient box into a high-impact target.

Licensing is layered

The Core project metadata identifies Apache-2.0, while the Studio code in the repository is separately marked AGPL-3.0. Review the relevant licence before redistributing or embedding.

Use the deck to understand the system. Use the repository, current docs, and your own measurements to make the final engineering decision.
Sources: pyproject.toml · Core metadata licence; Studio licence; Docker security notes.
